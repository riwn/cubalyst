# Phase 9 実装計画：ジャイロによる持ち替えの記録

## ゴール
ジャイロのあるキューブ（GAN i4 で確認済み）で、ソルブ中の持ち替え（y・x・z）を検出して記録する。
解法の表記は、その時点の持ち方で書けるようにする（`y R U R'`）。
解析には「認識」の時間のうち、持ち替えに使った時間を分けて渡す。

## わかっていること（2026-10-27 に実機で確認）
- i4 は `GYRO` イベントを送る。クォータニオンの大きさはほぼ 1 で、手で回した向きと合う
- 届く頻度は約 11 回/秒（約 90ms ごと）。持ち替え（0.2 秒前後）の途中は 2〜3 サンプルしか取れないが、前後で落ち着いた向きを比べれば 90° 単位で区別できる
- 角速度 `velocity` は常に `(0, 0, 0)`。使わない（回っているかどうかはクォータニオンの差で見る）
- ジャイロはコアに付いている。面を回してもコアは回らないが、**M や r などはコアごと回る**ので、x として現れる（後述）

## 方針
- **生データ（ジャイロのサンプル）を保存し、持ち替えはそこから計算する派生データにする**（回転ログと段階の区切りと同じ考え方）。
  検出のしきい値を変えても、過去のソルブを計算し直せる
- **回転ログ（`moves`）には混ぜない**。回転ログは、キューブ自身の向きでの面の回転の列のままにする。
  `moves` に y などを入れると、手数・段階の区切りの位置（`start_index`）・状態の再生（kpuzzle に適用すると状態ごと回ってしまう）が壊れる
- 持ち替えは、**持ち方の移り変わり（下の色・前の色）の列**として持つ。今の設定の「持ち方」と同じ形で、`holdFrame` / `notation.NewFrame` がそのまま使える
- 検出はフロント（TypeScript）で行い、段階の区切りと同じく、ソルブと一緒にサーバーへ送る。再計算もフロントの `recompute.ts` に足す
- ジャイロのないソルブ（過去の記録・ほかのキューブ・モック）は、今までどおり設定の持ち方で固定して扱う

## 検出のしかた

### 基準
2026-10-27 に実機で確かめた結果（i4、ファームウェア 1.15）：
- **クォータニオンの基準の Z 軸は鉛直上向き（重力に合っている）**。つないだときの向きに関係なく、白・緑・赤を上にして置くと、それぞれの色が上と読めた（ずれは 1° 前後）
- `q` は「キューブの座標 → 基準の座標」の回転。上の方向をキューブの座標で表すと `up(t) = q(t)* · (0, 0, 1) · q(t)`
- キューブの軸は +X 赤・+Y 青・+Z 白（ライブラリの説明どおり）
- 水平の向き（基準の X・Y 軸の方向）は決まっていない。机の上で水平に回すと、Z 軸まわりの回転だけが変わった。止めている間の値は 0.001 程度しか動かない

これを踏まえて、
- **下の色は、仮定なしに重力から決める**。`up(t)` に一番近い軸の色の反対が下の色
- **前の色だけ、着手の時点で設定の前の色だと仮定する**。着手の時点の下の色が設定の下の色と同じなら、そのときの水平の向きを「前」の基準にする
  - 下の色が設定と違う（クロスを別の色で組んだ、など）ときは、前の色を決められないので、そのソルブは持ち替えの記録なしとする（生のサンプルは残す）。手の記号の変換は、設定の持ち方で固定する（今の動き）
- 着手前の 0.5 秒のサンプルも残す。着手の時点の向きは、最初の手の直前のサンプルを使う（軸から 30° 以内なら持ち方は決まり、前の方向のずれもその範囲で吸収される）

### 持ち替えの確定
1. 各サンプルで、今の持ち方の候補（24 通りのどれか）を出す。いちばん近い向きとのずれが 30° を超えるサンプルは「回っている途中」とする
2. 同じ候補が 2 サンプル（約 180ms）続いたら、その持ち方に移ったと確定する
3. 移る前の最後の落ち着いたサンプルの時刻を `start_t`、確定した最初のサンプルの時刻を `end_t` とする
4. 持ち替えの名前は、前後の持ち方から決める（ユーザーの軸で見た回転。`y`・`y'`・`y2`・`x`・`z'`・`x y` など。x・y・z を組み合わせた手数が最も少ない書き方を、24 通りの表として作っておく）

面を回している最中の手の揺れや、少しずつのずれ（ドリフト）は、「落ち着いたら 90° 単位に丸める」ことで吸収する。

### M・r などのコアが回る手
r は `L` + `x`、M は `R L'` + `x'` として現れる（キューブは面の回転だけを報告し、コアの回転はジャイロに出る）。
表記をまとめる（`L` の直後の `x` を `r` にする、など）のは後回しにし、まずは x として記録する。
`x` が、`L`・`R` の回転と 150ms 以内に起きたものは「持ち手の回転ではなく、ワイドムーブやスライスの一部かもしれない」という印（`with_move`）を付けておく。

## 保存の形

マイグレーション `0009_gyro.sql` で `solves` に列を2つ足す。

```sql
ALTER TABLE solves ADD COLUMN gyro  TEXT NOT NULL DEFAULT '';  -- JSON: [[t, w, x, y, z], ...]（生データ）
ALTER TABLE solves ADD COLUMN holds TEXT NOT NULL DEFAULT '';  -- JSON: 持ち替えの列（派生データ）
```

- `gyro`：着手 0.5 秒前から完成までのサンプル。`t` は回転ログの `t` と同じ「ソルブ開始からの相対 ms」。値は小数 4 桁に丸める。
  20 秒のソルブで約 220 サンプル・約 8KB。空文字列は「ジャイロなし」
- `holds`：

  ```json
  {
    "start": { "bottom": "white", "front": "green" },
    "changes": [
      { "index": 9, "start_t": 4120, "end_t": 4390, "bottom": "white", "front": "red", "rot": "y'", "with_move": false }
    ]
  }
  ```
  - `index`：回転ログで、この持ち替えより前にある手の数（`moves[index]` 以降が新しい持ち方）
  - `rot` は前後の持ち方から決まる（設定に左右されない）ので、表示や解析で計算し直さずに使えるよう、一緒に保存する
- 段階の区切りと違って行ごとに検索する用途がないので、別テーブルにせず JSON の列にする
- 一覧の API（`GET /api/solves`）は、今の `moves` と同じく、頼まれたとき（`include=moves`）だけ `gyro` を返す。`holds` は小さいので常に返す
- JSON export にも両方を入れる

## ジャイロのオン・オフと、ジャイロが届かないとき

### 電池を節約できるのはキューブ側だけ
- ジャイロのデータは、回転と同じ通知（Gen4 は1本の characteristic）で届く。アプリでジャイロだけ受け取りを止めることはできない
- 接続ライブラリ（`smartcube-web-bluetooth`）には、キューブのジャイロを切り替える命令が無い（`REQUEST_FACELETS`・`REQUEST_HARDWARE`・`REQUEST_BATTERY`・`REQUEST_RESET` だけ）。命令のバイト列も公開されていない
- つまり、**電池を節約するには、キューブ側でジャイロを切る**必要がある。アプリの設定でできるのは「届いたデータを使うかどうか」だけ
- ユーザーは GAN のアプリの「省電力」設定でジャイロを切っている。**この設定はキューブ本体に残る**（2026-10-27 に確認。GAN のアプリで省電力をオンにして終了し、cubalyst でつないで傾けても `GYRO` は1件も届かなかった）。
  ジャイロを使いたいときは、GAN のアプリで省電力をオフにしてから cubalyst でつなぐ
- このとき、ライブラリの `capabilities.gyroscope` は `true`、`HARDWARE` の `gyroSupported` は `false` だった。どちらも「今ジャイロが届くか」を表さない
- 命令が分かれば、アプリからキューブのジャイロを切り替えられる（接続したときに、設定に合わせて送る）。今回は扱わず、分かったら足す

### アプリの設定「ジャイロで持ち替えを記録する」
- ⚙ の設定に足す（`settings` に `use_gyro`、既定はオフ）。オフのときは、届いたデータを貯めも保存もしない
- 持ち方の設定（下の色・前の色）は、オン・オフどちらでも使う（オンのときは着手時の持ち方として、オフのときは今までどおり固定の持ち方として）

### ジャイロが届いているかの判定
- ライブラリの `capabilities.gyroscope`（GAN では省電力でも true）も、`HARDWARE` の `gyroSupported`（データが1件届くまで false）も当てにしない
- 代わりに、**最後にジャイロのデータが届いた時刻**で判定する。接続後に一度でも届いていて、直近 2 秒以内に届いていれば「届いている」
- 接続パネルに、次のどれかを出す

| 設定 | データ | 表示 |
|---|---|---|
| オン | 届いている | ジャイロ：記録中 |
| オン | 届いていない | ジャイロ：届いていません（GAN のアプリで省電力がオンか、ジャイロの無いキューブ）。持ち替えは記録されません |
| オフ | 届いている | ジャイロ：使っていません（キューブ側でオンのままです。GAN のアプリで省電力にすると電池が持ちます） |
| オフ | 届いていない | 何も出さない |

### ジャイロが無い・届かないときのソルブ
- 保存はそのまま行う。`gyro`・`holds` を空にし、今までどおり設定の持ち方で固定して扱う（表示・解析とも、今の動き）
- 解法・段階の表には「持ち替えの記録なし」と小さく出す（「持ち替え 0 回」とは区別する）
- **着手時の前の色**（2026-10-27 に追加）：ジャイロでは水平の向きが分からないので、最初は「着手時は設定の前の色」と仮定していた。実際は下の色だけそろえて、前はスクランブルに合わせて変えることが多い。前が違うと、手の記号が 90° ずれ、x と z も入れ替わる。そこで、下の色が設定と同じ 4 通りの前の色で持ち替えを計算し、持ち方の記号で「R の数 − B の数」が一番多いものを採る（`estimateHolds`。CFOP では R をよく回し、B はほとんど回さない）。B の数だけだと、R・U だけの手順で前と横の区別が付かない。2番目の候補との差が 3 未満なら、設定の前の色のまま。推定したかは `holds.estimated` に残す。実機のソルブ（102 手）では、前の候補ごとの R・B が 26・1／6・26／15・6／1・15 で、点数は 25・−20・9・−14 とはっきり分かれた
- **スライス（M）**（2026-10-27 に追加）：GAN は M を「R' L」として報告し、中心（ジャイロ）ごと x に回る（M' = R' L x、M = R L' x'、M2 = R2 L2 x2）。実機のソルブでは PLL の M2 が x2 の持ち替えとして数えられていた。L・R と同時の x 系（`with_move`）は持ち替えの回数と時間に数えず、L・R の組がそろうものは `slice`・`slice_moves` を付け、表記で M などの1語にまとめる。そろわないもの（`L [x]` ≒ r など）は `[x]` のまま
- **のぞき**：キューブを傾けて下や後ろの面を見て、すぐ戻す動きも、持ち替え（例：`y x` → `y' z`）として記録される。検出は分けず、解析のプロンプトとスキルで「すぐ元の持ち方へ戻る x・z 系の組は、のぞき（認識のための動き）」と読ませる
- **ソルブの途中で途切れたとき**（キューブ側で切った、電波が弱いなど）：サンプルの間が 3 秒を超えて空いたら、そのソルブは持ち替えの記録なしとして扱う（生のサンプルは残すので、後で扱いを変えれば計算し直せる）。途切れた区間の前後で持ち方が分からなくなるので、部分的には使わない。3 秒以内の途切れは、前後の持ち方でつなぐ（途切れの間の持ち替えは、時刻が途切れの幅だけあいまいになる）。最初は 1 秒にしていたが、実機（i4）の 1 回目のソルブで 1.02 秒の途切れがあり、0.3〜0.45 秒の途切れも何度もあった（2026-10-27）
- 計測待ち（ready）の時点で届いていなければ、そのソルブはジャイロ無しで記録する（途中から届き始めても使わない。基準の向きが取れないため）

### まとめの解析で、ジャイロのあるソルブと無いソルブが混ざるとき
- 持ち替えの数字（回数・時間）は、ジャイロのあるソルブだけで出し、「N 件中 M 件に持ち替えの記録あり」と添える
- 認識の時間などのほかの数字は、今までどおり全部のソルブで出す
- ジャイロのあるソルブが少ない（たとえば 5 件未満）ときは、持ち替えの数字を出さない

### GAN 以外のキューブ
- ライブラリは MoYu・GoCube などのジャイロも `GYRO` イベントとして渡すが、どの軸がどの色かはプロトコルごとに違う可能性があり、確かめられていない
- クォータニオンの軸と色の対応を、プロトコルごとの表として持つ。**実機で確かめたもの（今は GAN Gen4 だけ）だけを使い**、それ以外は「届いていない」と同じ扱いにして、接続パネルに「このキューブのジャイロには対応していません」と出す

## 接続とイベント
- `CubeEvent` に `{ type: 'gyro'; timestamp: number; q: { w, x, y, z } }` を足す（`timestamp` はライブラリが付けた PC 時刻。回転の `localTimestamp` と同じ時計）。GAN Gen4 以外のプロトコルでは流さず、代わりに `gyro-unsupported` を1回だけ流す
- `CubeStore` に、最後にジャイロのデータが届いた時刻を持たせ、「届いている」かを接続パネルに出す
- `CubeStore` は最新の向きを持つだけ（ログには貯めない。約 11 回/秒で再描画させないよう、購読者への通知は `moves` と同じく専用の Emitter にする）
- 設定がオンのときだけ、`SolveSession` が、計測待ち（ready）の間は直近 0.5 秒だけ、計測中は全部のサンプルを貯め、保存時に回転ログの `t` と同じ基準の相対 ms に直す（回転ログの PC 時刻と `t` の差の平均でずらす）
- 持ち替えの再計算は `PUT /api/solves/{id}/holds`（本文が null なら記録なし）。設定画面の「全ソルブの持ち替えを再計算」から呼ぶ
- モック接続に、持ち替えを流すボタン（y・y'・x）を足す。テストではクォータニオンの列を作って流す

## 表示
- ソルブ詳細の解法：持ち替えを入れて、そのときの持ち方で書く（`R U R' y U R U' R'`）。持ち替えの所要時間は小さく添える
- 段階の表に「持ち替え」の列（回数と時間）
- 再生：3D のキューブを、その時点の持ち方の向きに回す（`holdRotation` を時刻ごとに切り替える）
- ジャイロのないソルブは今までどおり（「持ち替えの記録なし」と小さく出す）

## 解析への渡し方（`internal/analysis/input.go`）
- 前提の「持ち替えは検出できないので長い間として現れる」を、ソルブごとに書き分ける
  - ジャイロあり：「持ち替え（y・x・z）はジャイロで検出し、解法に入れています。手の記号はその時点の持ち方での面の名前です」
  - ジャイロなし：今の文のまま
- 解法：手ごとに、その時点の持ち方の `Frame` で変換し、持ち替えを入れる（`notation.NewFrame` を持ち替えの数だけ作る）
- 段階の表：持ち替えの回数と時間を足し、「認識」を「持ち替え」と「それ以外（考えていた時間）」に分ける
  - 段階の境目から最初の手までの間にある持ち替えの時間を、その段階の「認識中の持ち替え」とする
- 長い間：間の中に持ち替えがあれば「（y' の持ち替え 0.27 秒を含む）」と添える
- 面の偏り：その時点の持ち方で数え直す（今は B・F が多く見えるのが、R・U に寄るはず）
- まとめ：1 ソルブあたりの持ち替えの回数、F2L のペアごとの回数、多い持ち替えの種類。ジャイロありのソルブだけで数え、件数を添える
- `with_move` の付いた x は「ワイドムーブ・スライスの一部の可能性」と書き添える
- MCP の `get_solve` / `get_solves` は同じ入力を返すので、自動で反映される。スキルの `references/reading-data.md` と、MCP サーバーの説明文の「前提」も直す

## 進め方
1. 設定とイベントと保存：`use_gyro` の設定、`CubeEvent` の `gyro`、届いているかの表示、サンプルの記録、マイグレーション、API・OpenAPI・export
2. 検出：`detectHolds(samples, moves, startHold)` を純粋な関数で作り、クォータニオンの列を合成したテストで確かめる（y・y2・x、揺れ、ドリフト、ワイドムーブ）。再計算に足す
3. 表示：ソルブ詳細の解法と段階の表、再生
4. 解析：入力の変更、テスト、スキルと MCP の説明文
5. 実機で数十ソルブして、しきい値（30°・2 サンプル・150ms）を見直す

## 決めておくこと
- 着手の時点で設定の持ち方で持っている、という仮定でよいか（インスペクションで違う向きのまま始めると、全体がずれる）
- キューブのジャイロを切り替える命令を調べるか（分かれば、接続したときにアプリの設定に合わせて送れる）
